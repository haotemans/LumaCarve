# ADR-0001 · 模块化单仓库与执行职责边界

- 状态：Accepted for architecture planning（已确立规划方向，渐进迁移）
- 影响范围：前端、后端、模型/数据目录、CI
- 日期：2026-11-01

## 背景

LumaCarve 同时包含 React 图像工作台、Graph 编辑器、Python API、模型下载、推理/训练执行和本地资产。现有代码可启动，但页面与服务仍有聚合模块，未来接入多模型会增加耦合。用户要求低资源占用、单一 `.venv`、完整 Markdown 可追溯与小粒度 Commit。

## 决策

1. **保持单仓库**：`frontend/`、`backend/`、`tools/`、`docs/` 是主要代码边界。
2. **单 Python 环境**：项目根目录一个 `.venv`；推理/训练是功能/依赖组，不是独立虚拟环境。
3. **单 Graph 工作流定义**：Web 参数模式是 Graph 节点暴露字段的视图；不运行第二套图引擎。
4. **资源调度模块独立于 HTTP 服务**：API 可在没有 CUDA 时启动；真正 GPU 执行必须在可控执行上下文中运行。
5. **模型和数据不入仓库**：使用 `LumaCarveData`（可改位置），下载源、模型来源、缓存策略与项目文件分离。
6. **按功能组织前端源码**：新页面进入 `features/<domain>`，复用组件才进入 `components/`。
7. **文档与测试跟随模块**：代码与说明同步变更；CI 检查模块索引。

## 暂不做

不立即重命名所有 Python 包、不提前上微服务和消息队列、不在未验证模型完整性前全局复用权重、不为了目录整齐自动搬迁用户数据。

## 代价

迁移期会同时存在部分旧 `pages/` 文件和新 `features/` 文件。每次只迁移一个功能以保证 CI 可追踪；结构文档必须明确当前/目标状态，避免误导。
